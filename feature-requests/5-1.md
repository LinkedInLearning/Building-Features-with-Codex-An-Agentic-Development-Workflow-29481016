# Feature 1: Search and filtering

## 1. The problem

Support agents scroll the full ticket list to find one customer's issue or every urgent ticket. As the queue grows, that's slow and easy to get wrong.

## 2. Expected behavior

- [ ] A search box matches the ticket **title** or **customer** name.
- [ ] Search ignores capitalization and spaces before or after the text.
- [ ] A **Status** filter offers All, Open, In Progress, and Resolved.
- [ ] A **Priority** filter offers All, Low, Medium, and High.
- [ ] Choosing All for a filter means that filter is ignored.
- [ ] Search, status, and priority work together: a ticket shows only if it matches all three.
- [ ] The result line reads `Showing X of Y tickets` and updates as filters change.
- [ ] A **Clear filters** button resets the search box and both filters.
- [ ] When nothing matches, the existing "No tickets found" empty state appears.

## 3. Limits

- Non-goals: saving filters between visits, sorting, filtering by category or assignee.
- Constraints: no new dependencies. Keep the existing React structure.
- Must keep working: ticket cards look and behave the same as they do today.

## 4. How we'll prove it works

- Tests: put the filtering logic in a reusable function and test case-insensitive search, each filter on its own, combined filters, and a search with no matches.
- Manual check: type a customer name, change both filters, confirm the count, clear everything, and trigger the empty state.
